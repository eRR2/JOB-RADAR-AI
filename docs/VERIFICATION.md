# V1 verification evidence

Verified on Windows, 2026-10-11, in an independent checkout. All authored profiles/CVs were synthetic; live job content came from actual source responses. Private payloads and verification databases/scripts are ignored and not distributed. The user’s older JOB-RADAR checkout was read-only reference.

## Automated and installation checks

- **51 Python unittest tests passed**: readable synthetic PDF/DOCX extraction and contact redaction; strict profile/provider/schema validation; unknown salary versus hard constraints; exact CV/job quotes; expanded-candidate second selection; valid empty versus partial pagination/source failure; restriction/pending stops; invalid/incomplete response refusal; persistent request spacing; non-sliding cache freshness; real process timeout/cancellation; identity deduplication and preserved closed-banner evidence on search-only rediscovery; independent feedback/application histories; restart, corruption refusal, transaction rollback, consistent backup/restoration; overlap/skipped runs; scheduled interrupt cleanup; local daily/weekly scheduling; fixed native task command; guarded HTTP assets/actions, cross-origin/Host/CSRF refusal, reset/edit gates during AI, follow-up-answer acceptance and explicit deletion confirmation.
- **74 Bun upstream/safety tests passed**, 136 assertions. The subprocess test helper now preloads an empty fetch response, so argument tests are offline. Upstream originally had two valid-argument cases capable of making network requests; these were identified after earlier test invocations and isolated before release. Controlled live workflow measurements below refer to the deliberate application runs, not those earlier upstream smoke tests.
- `node --check web/app.js` passed. Native DOM/text construction, fixed links, dialog labeling, keyboard-focus/reduced-motion/responsive styles were inspected in source; this does **not** substitute for visual/browser accessibility QA.
- `setup.cmd` completed with exact locked wheels installed. Real module launcher started both isolated-verification and clean first-launch servers; default-browser launch was invoked. It binds only to 127.0.0.1.
- OSV batch query for six pinned PyPI runtime distributions returned no known advisories at verification time. Installed metadata confirmed the MIT / BSD-3-Clause license entries. This is an advisory database snapshot, not proof of absence of vulnerabilities.
- Canonical and both platform `SKILL.md` packages passed the installed skill-creator validator; relative references were inspected. Codex app-server `skills/list` actually discovered `.agents/skills/job-radar-ai/SKILL.md` as enabled. Claude Code is absent, so Claude discovery cannot be claimed live.

## Real AI and source execution

Installed environment: Python 3.13; Bun 1.4.2; Codex CLI 0.161.0, detected ChatGPT subscription login. No Claude Code or GitHub CLI was installed. Existing Git Credential Manager GitHub session was verified without printing or persisting its credential; publication uses that existing session.

1. A real bounded Codex probe returned schema-valid inference. No API key fallback or unrestricted shell/browser tool was used.
2. First live hunter run: the AI generated a query from the synthetic physical-product systems-leadership profile; actual upstream search returned **10 listings**, and actual detail retrieved **one full description** (ARX Robotics, Engineering Manager — Vehicle Integration, LinkedIn identity `4465201211`). The AI attempted to place employer qualifications into the user-hard-requirement array. Validation correctly refused the assessment; the run remained **partial** with all listings preserved. The prompt was corrected to distinguish employer criteria from user requirements and to state the 0–100 scoring scale and concise-query rule.
3. A real reassessment of that stored description then completed with valid exact job/CV evidence, separate ATS/HR analysis, unknown salary/work arrangements and a stretch-role recommendation. No new source request was required.
4. Explicit synthetic dislike feedback requested multidisciplinary team leadership from day one rather than initial individual vehicle-integration delivery. A later real reassessment changed **recommend=true / score 80.0** to **recommend=false / score 61.2**, with the reason matching the actual responsibilities. It explicitly avoided excluding the employer or automotive field. The score is a subjective AI preference assessment, not a calibrated probability.
5. A second full live hunter run completed without warnings: actual AI learning produced a **tentative**, feedback-ID-backed role-scope preference; actual AI generated the new query `engineering team leadership multidisciplinary physical products`, selected a description, and produced a schema/quote-validated assessment and report. Counts: **9 new / 1 previously seen / 1 description / 1 assessment / 2 LinkedIn requests**. The two deliberate live discovery runs used at most two source requests each, one search page and one description.
6. Repeating the original successful search used one cache hit, **zero new requests**, **10 returned / zero new records**, with 10 total records before and after that repeat. Later full discovery brought the combined database to **19 distinct jobs**.
7. Supplementary Codex research exercised **two actual web actions** (one search and one open) against public official employer/ATS sources. The open failed; the model returned no verified jobs and an explicit limitation. Full page text was not exposed through the adapter. V1 refuses supplementary imports on that evidence boundary; it does not turn model-proposed URLs into verified vacancies.

No claim of complete coverage or confirmed vacancy openness was made. No source denial was bypassed, native task created, application submitted, email sent or personal CV used.

## Actual local HTTP verification

On the isolated live-data server, `/api/state` returned 19 jobs, four persisted runs and two real AI evaluations for dashboard consumption. Saved → Applied → Rejected HTTP actions updated one intended identity and preserved the three dated events. A real synthetic DOCX upload passed through the parser subprocess, persisted locally and removed its synthetic email. Actual Codex profile interpretation via the API completed, generated a career proposal with three follow-up questions, and the review/acceptance API persisted the interpreted profile.

On the separate untouched first-launch workspace, `/`, `/app.js` and `/style.css` returned HTTP 200 with expected MIME/CSP headers. Initial profile was null and jobs empty, so onboarding is the actual initial state; no test discoveries were seeded into the user's default workspace. Persistent onboarding/action routes also passed synthetic HTTP tests.

**Browser automation was unavailable:** the connected computer-use inventory reported no browser surfaces, and in-app-browser creation returned Browser unavailable. Actual rendered visuals, browser click flows and accessibility auditing remain unverified. HTTP success and JavaScript parsing are not represented as a real browser test. The default browser is launched for the user to inspect.

## Review and release boundaries

The installed `karpathy-guidelines`, using-agent-skills, planning-and-task-breakdown, incremental-implementation, git-workflow-and-versioning, test-driven-development, security-and-hardening, frontend-ui-engineering, source-driven-development, api-and-interface-design, code-review-and-quality and documentation-and-adrs workflows were applied, alongside openai-docs and skill-creator. Browser-testing/computer-use instructions were inspected, but their unavailable browser capabilities are not counted as successful browser QA. No unrelated personal skills were changed.

An independent read-only review identified authentication-mode gating, stale assessments, concurrent preference mutation, unverifiable secondary content, expanded-result selection and cross-run spacing. Those defects were corrected and covered by focused tests. Publication additionally requires a complete tracked/staged/history private-data scan, ignore-rule checks and a source diff review. GitHub creation must target a new repository, never overwrite an existing one, and use the existing authorized session.

Known boundaries: Claude adapter implemented and contract-tested but not live-tested; secondary page-content verification unavailable; visual browser QA unavailable; native task creation approval-gated but not executed; macOS/Linux unverified; no hard PDF-parser memory isolation or encrypted local state. Source/AI failures remain visible and data is retained.
